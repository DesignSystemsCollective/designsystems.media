# ADR 0006: Convert video-aggregator to TypeScript

## Status

Accepted

## Context

`video-aggregator/scripts/` (`shared.js`, `youtube.js`, `vimeo.js`, `podcast.js`, `getVideos.js`, `getPodcasts.js`, `getImages.js`) was the last untyped corner of the codebase - `src/lib/content-domain` and the site's own utilities are already TypeScript. Video/episode/show shapes were duplicated ad hoc as inline object literals across files rather than defined once, and nothing caught a typo or a mismatched field name until it either crashed at runtime or (worse) silently wrote wrong data into a `.mdx` file.

## Decision

**Module system: kept CommonJS, not ESM.** Every file still uses `require()`/`module.exports`, unchanged in structure - this conversion adds type annotations, it doesn't restructure how the files load each other. The reason is Node's native TypeScript execution: this repo has no build step for video-aggregator (scripts run directly via `node`), and Node's type-stripping (`--experimental-strip-types`, already required by `test:unit` since Phase 0) only supports *erasable* syntax. Plain `require()` calls are erasable; TypeScript's own `import x = require(...)` interop syntax is not - it needs an actual transform, not just erasure, and would require a different, less broadly-supported stripping mode. So every file uses `import type { X } from "./types"` for compile-time-only type imports (fully erasable) alongside ordinary `const x = require("y")` calls (unchanged from the original JS, and untyped - `require()`'s return is always `any`).

**Cross-file generics don't work through `require()`.** `shared.ts`'s `loadJsonFile<T>()` is a real generic, but calling it as `loadJsonFile<Source>(...)` from another file fails to compile ("untyped function calls may not accept type arguments") - because `require("./shared.ts")`'s return type is `any`, and generic type arguments can't flow through an untyped call. Every call site that needs a typed result uses `loadJsonFile(path) as Source[]` instead. This is a real limitation of staying on CommonJS; it would go away under ESM `import`, which is one reason a future move to ESM (not undertaken here - see Consequences) might be worth it independently of this conversion.

**Runtime execution: Node's native stripping, no new dependency.** `npm run videos`/`podcasts`/`images` now invoke `node --experimental-strip-types video-aggregator/scripts/get*.ts` directly - no `ts-node`/`tsx` added. Verified this is safe for every place these scripts actually run: the three GitHub Actions workflows that call `npm run aggregate`/`podcasts`/`images` (`addPodcasts.yml`, `manual.yml`, `schedule.yml`) all use `node-version: latest`, comfortably past the version where stripping needs no flag at all. (`main.yml`, pinned to Node 20, calls a `generate-mosaics` npm script that doesn't exist in `package.json` - a separate, pre-existing break unrelated to this conversion, not touched here.)

**Typing philosophy: type this file's own inputs/outputs; leave large external API shapes as `any`.** Two categories of untyped data flow through these files: (1) values *this codebase* constructs and passes around - video/episode/show objects, function parameters and returns - and (2) raw responses from YouTube/Vimeo/Podcast Index's APIs, which are deeply nested, only partially consumed, and not worth modeling exhaustively for a conversion pass. Category 1 is fully typed against new shared types in `video-aggregator/scripts/types.ts` (`Video`, `Episode`, `Show`, `Source`, `PodcastSource`, `Frontmatter`, `PosterThumbnailSource`). Category 2 (`item`, `response.data`, `feed`, `contentDetails`, etc.) is explicitly `any`. This matches what actually catches bugs: a typo in a field name on a `Video` object being written to disk is a real bug worth catching; modeling every field YouTube's API could theoretically return is not this pass's job.

**`getImages.ts` is the one file that stays intentionally loose.** Its `data` object (parsed frontmatter via `gray-matter`) is left untyped rather than cast to `Frontmatter` at every property access, because this file's entire job is reading/mutating/rewriting three structurally different content shapes (show/episode/media) through the same code paths. Fighting that with casts at every `data.image`/`data.localImages` site would add noise without catching anything real. `updateMarkdownFile`, which just serializes "some object" generically, does take a typed `Frontmatter` parameter - that's a case where the looser type is actually the right one.

**Two behavior-identical fixes required by the type checker**, not style changes:
- `combinedVideoData.sort((a, b) => new Date(b.publishedAt) - new Date(a.publishedAt))` doesn't compile - TypeScript rejects arithmetic on `Date` operands directly (`Date - Date` needs `'any' | 'number' | 'bigint'`), even though it works at runtime via `Date`'s implicit `valueOf()`. Changed to `.getTime()` on both sides, which is exactly what the implicit coercion was already doing - zero behavior change, same in `getVideos.ts` and `getPodcasts.ts`.
- `podcast.ts`'s `generateApiHeaders()` builds a hash from `API_KEY + API_SECRET + apiHeaderTime`, where the env vars are `string | undefined`. Fixed with `as string` assertions at declaration, not `|| ""` defaults - an assertion doesn't change the runtime value at all if the vars are ever actually missing (still `undefined`, still produces the same `NaN` hash input as before - confirmed live during Phase 4 verification, see Consequences), where a default would have changed what gets hashed.

**One field required a non-null assertion to avoid a silent behavior change:** `getVideos.ts` originally read `video.thumbnails.high.url` directly; typing `high` as optional (matching `VideoThumbnails`) meant the type checker required a null check. Optional chaining (`high?.url`) was the obvious fix but would have silently changed a throw into an `undefined` value if `high` were ever actually missing. Used `video.thumbnails.high!.url` instead - a non-null assertion preserves the original throw-on-missing behavior exactly, rather than quietly weakening it as an unplanned side effect of adding types.

## Consequences

**Two pre-existing bugs surfaced during this conversion, not fixed here:**
- `getVideos.ts` calls `getAllVideosFromVimeo()`, which `vimeo.ts` has never exported (only `getVideoDataFromVimeo(videoId)`, a different, single-video signature exists). Separately, `sources.json`'s Vimeo entry is typed `"vimeo-channel"`, but the handler map only recognizes `"vimeo"` - so the mismatched call is never actually reached. Vimeo ingestion is currently fully inert, confirmed live: running `npm run videos` prints `Unknown source type: vimeo-channel` and skips it every time.
- `getPodcasts.ts`'s `ShowManager.createShow`/`findExisting` don't guard against a `null` feed object. When a feed fetch fails for any reason (missing API credentials, network error, bad feed URL - `getPodcastByFeedUrl` already catches its own errors and returns `showData: null` for exactly this reason), `createShow(null)` crashes on `feedData.id`, which propagates out of `main()`'s try/catch as a fatal error and stops the *entire* ingestion run on the first failing source, not just that one source. Confirmed live during this conversion's end-to-end verification (`npm run podcasts` in a sandbox with no configured Podcast Index credentials crashed immediately with `Cannot read properties of null (reading 'id')`).

Both are real, pre-existing in the original JS exactly as they are now - this conversion preserved them faithfully rather than fixing them as a side effect, consistent with every other phase in this refactor. Worth a dedicated follow-up; the second one in particular means a single bad feed can currently take down an entire scheduled ingestion run.

**`shared.ts`'s generics are only useful within `shared.ts` itself.** As noted above, the `require()` boundary means `loadJsonFile<T>()`'s generic can't be leveraged from other files today; every external call site casts the result with `as` instead. Not a regression (the original JS had no typing at all here), but worth knowing if a future contributor wonders why a "generic" function is always called without its type parameter.

**Verified behavior-preserving** the same way every prior phase in this refactor was: `test:unit` (56/56) passing before and after each file, `tsc --noEmit` showing zero *new* errors at each step (one pre-existing, unrelated error in `src/types/media.ts` was present before this phase and is untouched by it), and running the actual `npm run videos`/`podcasts`/`images` entry points end-to-end in a sandboxed environment (network calls fail there, but every failure path was already wrapped in the original code's own error handling, and no unintended file writes occurred - confirmed via `git status` after each run).
